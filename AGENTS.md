# Lynx: руководство для AI-агентов

## Обзор проекта

Lynx — PHP-библиотека для генерации классов доступа к MySQL по PHP-классам моделей. Это прежде всего генератор кода, а не законченный ORM общего назначения. Модель описывается атрибутами `#[Table]` и `#[Column]`; генератор создаёт репозитории, PDO-подключение и кеш подготовленных выражений.

Проект находится в активной разработке. Сейчас `Build` генерирует Provider, Create и Delete для каждой модели, а также общие `Database` и `CachePDO`. Delete пока только накапливает условия фильтров и не выполняет SQL. `UpdateEntity`, `UpdateBulkEntity`, `CreateBulk`, `QueryBuilder` и большая часть `Scanner` являются заготовками. Актуальный список планов находится в `tech-doc.md`.

## Технологический стек и требования

- PHP; для текущего исходного кода практически требуется PHP 8.3 или новее: используются типизированные константы классов, а dev-зависимость Pest 4 требует PHP 8.3. В `composer.json` ограничение версии PHP пока не объявлено.
- Composer; пакет имеет тип `library` и имя `lynx/lynx`.
- Обязательное расширение `ext-pdo`. Для фактического подключения сгенерированного кода к MySQL также нужен драйвер `pdo_mysql`.
- `nikic/php-parser` 5.7 — разбор и форматирование сгенерированного PHP-кода.
- Pest 4.3 / PHPUnit — тесты.
- PHPStan 2.1 — статический анализ.
- MySQL 8.4.5 в `docker-compose.yml`; PHP-приложение в Docker-контейнер не помещено.

PHP-фреймворк, JS-инструменты и отдельная система сборки не используются.

## Структура и поток генерации

Основной сценарий:

1. Вызывающий код создаёт `Lynx\Config\Config`, явно перечисляет классы моделей через `setClasses()` и задаёт пространство имён, каталог вывода и параметры БД.
2. `Lynx\Parser\Parser` через Reflection API читает атрибуты классов и типизированных свойств и создаёт объекты метаданных.
3. `Lynx\Build\Build` последовательно вызывает генераторы.
4. Генераторы возвращают `DataForSaveFile`; `Lynx\IO\File` парсит код через `nikic/php-parser`, форматирует его и записывает PHP-файлы.

Основные каталоги и модули:

- `src/Lynx/Attributes/` — `Table`, `Column`, `Ignore`. `Column` содержит имя столбца, `notNull` и `autoIncrement`; `Ignore` объявлен, но текущий `Parser` его не обрабатывает.
- `src/Lynx/Config/Config.php` — fluent-конфигурация генерации.
- `src/Lynx/Parser/Parser.php` — преобразование моделей в метаданные. Классы не ищутся автоматически: их список передаётся в конфигурации. У модели должны быть имя таблицы, атрибуты столбцов и типы свойств.
- `src/Lynx/DataClasses/` — DTO метаданных и параметров записи; часть классов объявлена `readonly`.
- `src/Lynx/Generator/` — генераторы Provider, Create, Delete, Database и CachePDO. Все действующие генераторы реализуют `IGenerator`.
- `src/Lynx/IO/File.php` — создание каталогов, pretty-print и запись файлов.
- `src/Lynx/Build/Build.php` — единая точка оркестрации генерации.
- `src/Lynx/Scanner/`, `src/Lynx/Query/` — пока не участвуют в основном сценарии.
- `index.php` — основной локальный пример запуска: объявляет модели, настраивает `Config` и вызывает `Build::buildCode()`. Это не универсальный CLI.
- `lxc.php`, `lynx.php`, корневой `Ignore.php` — экспериментальные/примерные файлы, не часть основного API генератора.
- `generated/` — локальный результат генерации; каталог указан в `.gitignore`, поэтому не следует считать его исходным кодом библиотеки или редактировать вместо генераторов.

При `setNamespace("Ptr")` и каталоге вывода `generated` создаётся структура:

```text
generated/
├── Cache/CachePDO.php
├── Database/Database.php
└── Repository/<Model>/
    ├── <Model>.php
    ├── <Model>Create.php
    └── <Model>Delete.php
```

Пространства имён результата: `Ptr\Cache`, `Ptr\Database` и `Ptr\Repository\<Model>`. Автозагрузку этого результата должен настроить проект-потребитель.

### Сгенерированная runtime-архитектура

- `Database` создаёт ленивый статический экземпляр и возвращает PDO с DSN `mysql:host=...;dbname=...;charset=...`. Включены исключения PDO, ассоциативные результаты и native prepares (`PDO::ATTR_EMULATE_PREPARES = false`).
- `CachePDO` хранит `PDOStatement` в статическом массиве по строковому ключу.
- `<Model>` предоставляет статические `create()` и `delete()` и кеширует соответствующие builder-объекты.
- `<Model>Create` имеет fluent-сеттеры полей и `save()`, который строит параметризованный `INSERT`, кеширует statement по MD5 SQL и выполняет его.
- `<Model>Delete` создаёт fluent-методы `Eq`, `NotEq`, `Gt`, `GtEq`, `Lt`, `LtEq`, `In`, `NotIn`, но метод выполнения удаления ещё не реализован.

## Установка, генерация и проверки

В корне проекта:

```bash
composer install
php index.php
php vendor/bin/pest
php vendor/bin/phpstan analyse --no-progress
```

`php index.php` использует именно модели и параметры, записанные в этом файле, и перезаписывает одноимённые файлы в `generated/`. Само построение кода не подключается к БД; подключение происходит только при выполнении сгенерированных операций. Перед запуском примера проверьте `Config`, чтобы не перезаписать нужный локальный результат.

В `composer.json` нет секции `scripts`, поэтому готовых команд `composer test`, `composer analyse` или отдельной production-сборки нет. Обычные `vendor/bin/...` также допустимы, если файлы имеют executable-бит; вызов через `php` работает независимо от него.

Для локального MySQL:

```bash
docker compose up -d mysql
```

Docker Compose публикует порт `3306`, создаёт БД `server_profiles`, пользователя `myuser` и root-пароль из compose-файла. Эти значения не совпадают с примером `test_db`/`root` в `index.php`; перед реальным подключением конфигурацию нужно согласовать вручную.

### Текущее состояние проверок

- `composer validate --no-check-publish` проходит с предупреждением об отсутствии лицензии.
- Pest сейчас завершается до запуска тестов с ошибкой `Tests\TestCase was not found`. `tests/Pest.php` привязывает Feature-тесты к этому классу, но в `composer.json` нет `autoload-dev` для пространства `Tests\`, а bootstrap в `phpunit.xml` подключает только `vendor/autoload.php`.
- PHPStan запускается с `phpstan.neon` (уровень 10, пути `src` и `tests`) и на текущем коде сообщает 41 ошибку. Не выдавайте эти существующие ошибки за следствие новых изменений; при работе над кодом сравнивайте результат с исходным состоянием.

## Стиль кода и соглашения

- Исходники библиотеки используют PSR-4: `Lynx\` соответствует `src/Lynx/`; сохраняйте соответствие пространства имён и пути.
- Классы — PascalCase, методы и свойства — преимущественно camelCase, имена столбцов БД — snake_case.
- Используйте строгие типы параметров/возвратов и свойств там, где это соответствует окружающему коду. Для массивов в сигнатурах добавляйте PHPDoc с типом элементов, особенно с учётом PHPStan level 10.
- DTO создаются через конструкторы с promotion; новые неизменяемые данные можно оформлять как `readonly` по образцу существующих классов. В генерации и конфигурации активно применяются именованные аргументы.
- Генераторы собирают PHP через heredoc-шаблоны и возвращают `DataForSaveFile`; путь и имя файла определяются в `dataForSaveFile()`, а не напрямую через файловые операции в генераторе.
- Изменения схемы метаданных нужно согласованно проводить через атрибуты, `Parser`, DTO и затронутые генераторы. Не исправляйте только текст в `generated/`: следующая генерация его перезапишет.
- Отдельного PHP-форматтера, линтера стиля или правил PSR-12 в конфигурации нет. Соблюдайте локальный стиль изменяемого файла; форматирование результата делает `nikic/php-parser`.
- Комментарии и документация проекта преимущественно на русском; шаблонные комментарии Pest и часть технических меток в коде — на английском.

## Тестирование

`phpunit.xml` рекурсивно находит файлы `tests/**/*Test.php`. Используются функциональные тесты Pest (`test(...)`, `expect(...)`), а не обязательные классы PHPUnit. `tests/TestCase.php` — базовый класс для Feature-тестов; общие расширения Pest находятся в `tests/Pest.php`.

Сейчас есть только два одинаковых placeholder-теста в `tests/Unit/ExampleTest.php` и `tests/Feature/ExampleTest.php`. Реальных тестов парсера, генерации SQL, записи файлов или интеграции с MySQL нет. При добавлении проверок генератора предпочтительно тестировать метаданные/сгенерированный код и использовать временный каталог, не перезаписывая локальный `generated/`. Для интеграционных тестов БД понадобится отдельно настроенная тестовая база; текущий набор её не создаёт.

## Публикация, развёртывание и безопасность

CI/CD, release-скриптов и процесса развёртывания в репозитории нет. Предполагаемый способ использования — подключение библиотеки как Composer-пакета и перенос сгенерированного кода в проект-потребитель.

`copy.sh` и `copy.bat` копируют `generated/` в отдельный локальный проект `orm-test`. Пути в них жёстко заданы для конкретной машины, а скрипты сначала рекурсивно удаляют каталог назначения. Не запускайте их без проверки и изменения путей.

Параметры БД передаются строками и вставляются прямо в сгенерированный `Database.php`; отдельной поддержки переменных окружения или секретов нет. Не помещайте реальные пароли в примеры, исходники генератора или публикуемый результат. Каталог `generated/` игнорируется Git, но существующие локальные файлы всё равно могут содержать учётные данные. Учётные данные в `docker-compose.yml` и `index.php` следует считать только локальными development-значениями, а не production-конфигурацией.

SQL-значения в Create передаются через prepared statements, однако имена таблиц и столбцов попадают в SQL из метаданных моделей. Источником таких метаданных должен быть доверенный код модели, а не пользовательский ввод.
